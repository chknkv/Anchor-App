## 1. BDUI: строковые ключи

### Принцип работы

Клиент реализует **BDUI (Backend-Driven UI)** для иконок, градиентов и категорий привычек. Сервер не знает ничего о Compose, DrawableResource или цветовых токенах — он оперирует только простыми строками. Клиент сам конвертирует эти строки в визуальные компоненты при отрисовке.

**Пример:**
- Сервер хранит и возвращает `"iconKey": "ic_habit_sport"` и `"gradientKey": "orange"`.
- Клиент получает строки, конвертирует `"ic_habit_sport"` в иконку бегуна, `"orange"` — в оранжевый градиент фона карточки.

**Почему так сделано:**
Отвязка визуального представления от данных. Если нужно поменять иконку для категории «Спорт», достаточно заменить ресурс в клиенте без изменения API. Сервер хранит семантический ключ, а не бинарный ресурс.

**Правила:**

| # | Правило |
|---|---------|
| 1 | Ключи **case-sensitive**: `"orange"` ≠ `"Orange"`. Всегда использовать точное написание из таблиц ниже. |
| 2 | Бэкенд **не валидирует** ключи — он хранит и возвращает их как есть. Клиент никогда не отправит неизвестный ключ, бэкенд никогда не вернёт неизвестный ключ. |
| 3 | Если клиент всё-таки получит неизвестный ключ (например, при рассинхронизации версий) — краша не будет, покажется плейсхолдер. Это защитный механизм клиента, не норма. |

---

### Категории привычек

Категория — строковый ключ, которым бэкенд маркирует группы привычек. Клиент конвертирует его в локализованное название.

| Ключ (`categoryKey`) | EN | RU |
|---|---|---|
| `lifestyle` | Lifestyle | Образ жизни |
| `health` | Health | Здоровье |
| `sport` | Sport | Спорт |
| `productivity` | Productivity | Продуктивность |
| `finance` | Finance | Финансы |
| `relationships` | Relationships & Growth | Отношения & Развитие |
| `other` | Other | Другое |

**Где используется:** в группировке привычек (`GET /client/addictions/all`), в деталях привычки (`GET /client/addictions/details/{id}`), в запросах на создание и обновление.

**При неизвестном ключе:** клиент не крашится, категория отображается как пустая строка.

---

### Иконки привычек

Иконка — строковый ключ, который идентифицирует визуальный символ привычки. Клиент конвертирует его в SVG-ресурс.

| Ключ (`iconKey`) | Категория (EN) | Категория (RU) |
|---|---|---|
| `ic_habit_lifestyle` | Lifestyle | Образ жизни |
| `ic_habit_health` | Health | Здоровье |
| `ic_habit_sport` | Sport | Спорт |
| `ic_habit_productivity` | Productivity | Продуктивность |
| `ic_habit_finance` | Finance | Финансы |
| `ic_habit_relationships` | Relationships & Growth | Отношения & Развитие |

**Где используется:** в списке привычек пользователя, в деталях, в запросах на создание и обновление.

**При неизвестном ключе:** клиент отображает нейтральный плейсхолдер без краша.


---

### Градиенты привычек

Градиент — строковый ключ цветовой темы карточки привычки. Клиент конвертирует его в вертикальный цветовой градиент фона.

| Ключ (`gradientKey`) | Цвет (EN) | Цвет (RU) |
|---|---|---|
| `gray` | Gray | Серый |
| `green` | Green | Зелёный |
| `blue` | Blue | Синий |
| `indigo` | Indigo | Индиго |
| `purple` | Purple | Фиолетовый |
| `pink` | Pink | Розовый |
| `orange` | Orange | Оранжевый |
| `dark_orange` | Dark Orange | Тёмно-оранжевый |
| `red` | Red | Красный |
| `dark_red` | Dark Red | Тёмно-красный |
| `black` | Black | Чёрный |

**Где используется:** в списке привычек пользователя, в деталях, в запросах на создание и обновление.

**При неизвестном ключе:** клиент отображает серый градиент (`gray`) без краша.

## 2. Общие правила сетевого контракта

### Авторизация

Все эндпоинты приложения требуют Bearer JWT-токена в заголовке запроса:

```
Authorization: Bearer <access_token>
```

**Исключения** — только эндпоинты авторизационного флоу (отправка OTP, верификация OTP, refresh токена). Они описаны отдельно в соответствующем разделе.

**Жизненный цикл токена:**

| Событие | Поведение |
|---------|-----------|
| Запрос выполнен успешно | Токен действителен, ничего не происходит |
| Сервер вернул `401` | Клиент автоматически выполняет `POST auth/refresh` с refresh-токеном и повторяет оригинальный запрос |
| `POST auth/refresh` вернул `401` | Токены удаляются, пользователь направляется на экран авторизации |
| `5xx` или сетевая ошибка | Токены сохраняются, клиент показывает ошибку без разлогинивания |

Логика обновления токена полностью скрыта внутри сетевого слоя клиента. Бэкенд реализует стандартный refresh-механизм; со стороны API это обычный `POST`-запрос.

---

### Конверт ответа NetworkEntity

Все эндпоинты Anchor API — без исключений — оборачивают ответ в единый конверт:

```json
{ "success": true, "body": { ... } }
```

```json
{ "success": false, "message": "Описание ошибки" }
```

**Почему так сделано:** единый конверт позволяет клиенту обрабатывать все ответы единообразно, независимо от типа данных. Клиент сначала проверяет `success`, и только при `true` — десериализует `body`. Это устраняет разрыв между семантикой HTTP-кодов (которые могут быть `200`, но с бизнес-ошибкой внутри) и фактическим результатом операции.

#### Поля конверта

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Признак успеха | `success` | `Boolean` | `true` — операция выполнена успешно; `false` — произошла ошибка на стороне сервера | **Всегда** |
| Тело ответа | `body` | `Object \| null` | Полезная нагрузка ответа. Присутствует только при `success: true` и только если эндпоинт возвращает данные. Для void-операций (удаление, обновление без возврата) — отсутствует или `null` даже при успехе | При успехе с данными |
| Сообщение об ошибке | `message` | `String \| null` | Человекочитаемое описание ошибки. Присутствует только при `success: false` | При ошибке |
| Признак таймаута | `timeout` | `String \| null` | Строковый маркер, если причина `success: false` — таймаут на стороне сервера | При таймауте |

> `message` и `timeout` используются клиентом только для внутреннего логирования. Пользователю они не показываются — клиент отображает собственные локализованные строки.

#### Примеры

```json
// Успешный ответ с данными
{
  "success": true,
  "body": {
    "id": 42,
    "name": "Бег по утрам"
  }
}

// Успешный void-ответ (операция без возврата данных)
{
  "success": true
}

// Ошибка
{
  "success": false,
  "message": "Запись не найдена"
}

// Таймаут
{
  "success": false,
  "message": null,
  "timeout": "request_timeout"
}
```

---

### HTTP-коды ответов

Клиент интерпретирует HTTP-статусы следующим образом:

| Код | Название | Когда используется |
|-----|----------|--------------------|
| `200 OK` | Успех | Стандартный ответ на любой успешно выполненный запрос (GET, POST, PATCH, DELETE) |
| `400 Bad Request` | Некорректный запрос | Запрос нарушает бизнес-правила или содержит невалидные данные. Клиент отображает экран ошибки |
| `401 Unauthorized` | Не авторизован | Access-токен истёк или невалиден. Клиент автоматически пытается обновить токен через `POST auth/refresh`. Если refresh тоже вернул `401` — пользователь разлогинивается |
| `403 Forbidden` | Доступ запрещён | Пользователь не имеет прав на данный ресурс. Клиент отображает экран ошибки |
| `404 Not Found` | Ресурс не найден | Запрошенный ресурс (привычка, пользователь и т.д.) не существует. Клиент отображает экран ошибки |
| `500 Internal Server Error` | Внутренняя ошибка сервера | Непредвиденная ошибка на стороне сервера. Клиент отображает экран ошибки |

**Коды, которые не приходят от сервера, но обрабатываются клиентом:**

| Ситуация | Как воспринимается клиентом |
|----------|-----------------------------|
| Нет сети / хост недостижим | Клиент показывает экран «Нет соединения» |
| Таймаут соединения или сокета | Клиент показывает экран «Нет соединения» |

> Клиент не различает `400`, `403`, `404` и `500` на уровне UX — все они приводят к показу экрана ошибки с кнопкой «Попробовать снова». Разделение кодов важно для корректной обработки на стороне бэкенда и логирования.

## 3.1 FeatureAuth — авторизация

### Описание модуля

Авторизация в Anchor построена на схеме **email → OTP**. Пароля нет. Пользователь вводит email, получает на него одноразовый код (OTP), вводит код — и получает пару токенов доступа.

Сессия OTP — это временный объект на стороне сервера, идентифицируемый строкой `sessionId`. Клиент передаёт `sessionId` при верификации и повторной отправке кода, чтобы сервер понял, к какой именно сессии относится запрос.

**Все три эндпоинта этого модуля не требуют Bearer-токена** — они вызываются до получения токена.

**Сценарий авторизации:**

```
1. POST auth/otp/send    → { email }              → sessionId
2. POST auth/otp/verify  → { sessionId, otp }     → accessToken + refreshToken + isFirstAuthorized
   (или, если код не пришёл)
   POST auth/otp/resend  → { sessionId }           → void
```

После успешного `verify` клиент сохраняет токены и направляет пользователя:
- `isFirstAuthorized: true` → онбординг (выбор привычек)
- `isFirstAuthorized: false` → главный экран

---

### POST `auth/otp/send`

Инициирует сессию авторизации: создаёт OTP и отправляет его на указанный email.

**Метод:** `POST`  
**Путь:** `auth/otp/send`  
**Требует токена:** нет

#### Тело запроса

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Email пользователя | `email` | `String` | Адрес электронной почты. Валидация формата — на стороне клиента до отправки запроса | **Обязательный** |

#### Модель ответа: `OtpSendBody`

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Идентификатор сессии | `sessionId` | `String` | Уникальный идентификатор OTP-сессии. Клиент хранит его и передаёт в последующих запросах `verify` и `resend` | **Обязательный** |

#### Примеры

```json
// Запрос
{
  "email": "user@example.com"
}

// Успешный ответ
{
  "success": true,
  "body": {
    "sessionId": "3f8a21bc-4e10-4d2f-a981-d1e2f3a4b5c6"
  }
}

// Ответ при ошибке (например, некорректный email на стороне сервера)
{
  "success": false,
  "message": "Invalid email format"
}
```

---

### POST `auth/otp/verify`

Верифицирует введённый пользователем OTP-код и при успехе выдаёт пару токенов доступа.

**Метод:** `POST`  
**Путь:** `auth/otp/verify`  
**Требует токена:** нет

> Клиент автоматически отправляет этот запрос в момент ввода 5-го символа кода — без дополнительного нажатия кнопки.

#### Тело запроса

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Идентификатор сессии | `sessionId` | `String` | Значение, полученное от `auth/otp/send` | **Обязательный** |
| OTP-код | `otp` | `String` | 5-значный цифровой код, введённый пользователем | **Обязательный** |

#### Модель ответа: `OtpVerifyBody`

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Токен доступа | `accessToken` | `String` | JWT. Используется клиентом в заголовке `Authorization: Bearer` для всех последующих запросов | **Обязательный** |
| Токен обновления | `refreshToken` | `String` | JWT. Используется для получения новой пары токенов через `auth/refresh`, когда `accessToken` истёк | **Обязательный** |
| Флаг первой авторизации | `isFirstAuthorized` | `Boolean` | `true` — пользователь авторизуется впервые, направляется на онбординг; `false` — повторная авторизация, направляется на главный экран | **Обязательный** |

#### HTTP-коды ошибок (специфичные для этого эндпоинта)

| Код | Причина | Поведение клиента |
|-----|---------|-------------------|
| `400` | OTP-код неверный | Показывает сообщение об ошибке под полем ввода, разрешает повторный ввод |
| `410` | OTP-сессия истекла | Возвращает пользователя на экран ввода email |

#### Примеры

```json
// Запрос
{
  "sessionId": "3f8a21bc-4e10-4d2f-a981-d1e2f3a4b5c6",
  "otp": "48291"
}

// Успешный ответ (новый пользователь)
{
  "success": true,
  "body": {
    "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refreshToken": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4...",
    "isFirstAuthorized": true
  }
}

// Успешный ответ (возвращающийся пользователь)
{
  "success": true,
  "body": {
    "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refreshToken": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4...",
    "isFirstAuthorized": false
  }
}

// Ответ при неверном OTP (400)
{
  "success": false,
  "message": "Invalid OTP code"
}

// Ответ при истёкшей сессии (410)
{
  "success": false,
  "message": "OTP session expired"
}
```

### POST `auth/otp/resend`

Повторно отправляет OTP-код на email, привязанный к существующей сессии. Клиент вызывает этот эндпоинт, когда пользователь нажимает кнопку «Отправить снова» — она становится активной после истечения таймера (60 секунд).

**Метод:** `POST`  
**Путь:** `auth/otp/resend`  
**Требует токена:** нет

> Этот эндпоинт не возвращает тела (`body`). Клиент проверяет только `success: true`.  
> Сессия (`sessionId`) остаётся той же — новый код привязывается к существующей сессии, а не создаёт новую.

#### Тело запроса

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Идентификатор сессии | `sessionId` | `String` | Значение, полученное от `auth/otp/send` | **Обязательный** |

#### Ответ

Тело ответа отсутствует. Клиент читает только `success`.

#### HTTP-коды ошибок (специфичные для этого эндпоинта)

| Код | Причина | Поведение клиента |
|-----|---------|-------------------|
| `410` | OTP-сессия истекла | Возвращает пользователя на экран ввода email |

#### Примеры

```json
// Запрос
{
  "sessionId": "3f8a21bc-4e10-4d2f-a981-d1e2f3a4b5c6"
}

// Успешный ответ
{
  "success": true
}

// Ответ при истёкшей сессии (410)
{
  "success": false,
  "message": "OTP session expired"
}
```

---

### POST `auth/refresh`

Обновляет пару токенов доступа. Клиент вызывает этот эндпоинт автоматически, когда сервер возвращает `401` на любой авторизованный запрос. Ручного вызова со стороны продуктового кода нет — это полностью внутренняя механика сетевого слоя.

**Метод:** `POST`  
**Путь:** `auth/refresh`  
**Требует токена:** нет (Bearer-токен не прикрепляется; вместо него в теле передаётся `refreshToken`)

#### Тело запроса

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Токен обновления | `refreshToken` | `String` | Действующий refresh-токен, ранее выданный через `auth/otp/verify` или предыдущий `auth/refresh` | **Обязательный** |

#### Модель ответа

| Параметр | JSON-ключ | Тип | Описание | Обязательность |
|----------|-----------|-----|----------|----------------|
| Новый токен доступа | `accessToken` | `String` | Новый JWT. Клиент использует его во всех последующих запросах | **Обязательный** |
| Новый токен обновления | `refreshToken` | `String` | Новый refresh-токен. Клиент заменяет сохранённый токен на этот | **Обязательный** |

#### Поведение при ошибках

| Код | Причина | Поведение клиента |
|-----|---------|-------------------|
| `400` / `401` / `403` | Refresh-токен невалиден или отозван | Клиент удаляет оба токена и направляет пользователя на экран авторизации |
| `5xx` / `429` / нет сети | Сервер недоступен | Токены сохраняются; пользователь видит экран ошибки, повтор произойдёт при следующем запросе |

#### Примеры

```json
// Запрос
{
  "refreshToken": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4..."
}

// Успешный ответ
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "bmV3UmVmcmVzaFRva2Vu..."
}

// Ответ при невалидном refresh-токене (401)
{
  "success": false,
  "message": "Refresh token is invalid or expired"
}
```

> **Замечание по формату ответа.** Клиент ожидает `accessToken` и `refreshToken` непосредственно в корне JSON — **без обёртки `NetworkEntity`**. Это единственный эндпоинт, который не следует общему конверту, так как обрабатывается внутри Ktor Auth-плагина, а не через стандартный `ApiClient`.

## 3.2 FeatureAddiction — привычки

### Описание модуля

Модуль управляет привычками пользователя: онбординг-выбор при первом входе, список привычек на главном экране, создание, редактирование, просмотр деталей и удаление.

Эндпоинты делятся на две группы:

- **`addictions/*`** — вызываются один раз при онбординге (сразу после авторизации). Возвращают дефолтный каталог привычек и сохраняют выбор пользователя.
- **`client/addictions/*`** — основные CRUD-операции над привычками конкретного пользователя.

Все эндпоинты требуют Bearer-токена.

> ⚠️ **Известные несоответствия в клиентском коде — требуют согласования:**
>
> 1. В `PATCH client/addictions/update/{id}` поле категории сериализуется как `"category_ley"` вместо `"category_key"` (опечатка в коде клиента). **Бэкенд должен ожидать `"category_key"`** — клиентский код будет исправлен.
> 2. В `GET client/addictions/all` поле градиента в элементе списка сериализуется как `"gradient"`, а не `"gradient_key"` (как во всех остальных эндпоинтах). Бэкенд должен возвращать именно `"gradient"` для этого эндпоинта.

| Краткий текст цитаты | `text` | `String` | Короткая версия цитаты. Отображается в карточке-карусели на главном экране. Рекомендуемая длина — до 80 символов | **Обязательный** |
| Расширенный текст цитаты | `detail_text` | `String` | Полная версия цитаты. Отображается в sheet при нажатии на карточку. Может быть длиннее `text` | **Обязательный** |

> Оба поля не могут быть `null`. Если цитата одна и та же в кратком и расширенном формате, допустимо передать одинаковый текст в оба поля.

#### Пример успешного ответа

```json
{
  "success": true,
  "body": {
    "text": "Маленький шаг каждый день — большая жизнь в итоге.",
    "detail_text": "Маленький шаг каждый день — большая жизнь в итоге. Не жди идеального момента, начни с того, что есть прямо сейчас."
  }
}
```

#### Пример ответа при ошибке

```json
{
  "success": false,
  "message": "Цитата не найдена"
}
```
