# Anchor — сетевой контракт

Данный документ описывает сетевой контракт между мобильным клиентом (KMP, iOS + Android) и бэкендом приложения Anchor.

> **Соглашение об авторизации.** Все эндпоинты, кроме авторизационного флоу (`auth/*`), требуют Bearer JWT-токена в заголовке `Authorization: Bearer <access_token>`. Токен выдаётся после успешной OTP-верификации и обновляется автоматически через refresh-механизм.

## 1. BDUI: строковые ключи

### Принцип работы

Клиент реализует **BDUI (Backend-Driven UI)** для иконок, градиентов и категорий привычек. Сервер оперирует только простыми строками. Клиент конвертирует эти строки в визуальные компоненты при отрисовке.

**Пример:**
- Сервер хранит и возвращает `"icon_key": "ic_habit_sport"` и `"gradient_key": "orange"`.
- Клиент конвертирует `"ic_habit_sport"` в иконку бегуна, `"orange"` — в оранжевый градиент фона карточки.

**Правила:**

| # | Правило |
|---|---------|
| 1 | Ключи **case-sensitive**: `"orange"` ≠ `"Orange"`. Всегда использовать точное написание из таблиц ниже. |
| 2 | Бэкенд **не валидирует** ключи — он хранит и возвращает их как есть. Клиент никогда не отправит неизвестный ключ. |
| 3 | Если клиент получит неизвестный ключ — десериализация упадёт с ошибкой. Бэкенд должен возвращать строго значения из таблиц ниже. |

## 2. Общие правила сетевого контракта

### Авторизация

Все эндпоинты, кроме `auth/*`, требуют заголовок:

```
Authorization: Bearer <access_token>
```

**Жизненный цикл токена:**

| Событие | Поведение |
|---------|-----------|
| Запрос выполнен успешно | Токен действителен |
| Сервер вернул `401` | Клиент автоматически вызывает `POST auth/refresh` и повторяет запрос |
| `POST auth/refresh` вернул `400` / `401` / `403` | Токены удаляются, пользователь направляется на экран авторизации |
| `5xx` или сетевая ошибка | Токены сохраняются, клиент показывает экран ошибки |

---

### HTTP-коды ответов

| Код | Название | REST-смысл | Когда использовать | Поведение клиента |
|-----|----------|------------|--------------------|-------------------|
| **200 OK** | Успех с телом | Операция выполнена, тело содержит ресурс | GET с данными; мутации, отдающие обновлённый ресурс | Десериализовать тело |
| **201 Created** | Ресурс создан | Ресурс создан, тело содержит его | POST с возвратом сущности (резерв, сейчас не используется) | Десериализовать тело |
| **204 No Content** | Успех без тела | Операция выполнена, тела нет | Мутации без возврата данных: save-selected, create, increment, update, delete | Не читать тело |
| **400 Bad Request** | Невалидный запрос | Запрос нарушает бизнес-правила или содержит невалидные данные | Неверный OTP, malformed payload | Показать ошибку |
| **401 Unauthorized** | Не авторизован | Токен невалиден или истёк | Любой защищённый эндпоинт без валидного токена | Автоматический refresh; при повторном 401 — разлогин |
| **403 Forbidden** | Доступ запрещён | Токен валиден, но прав недостаточно | Попытка доступа к чужому ресурсу | Показать ошибку |
| **404 Not Found** | Ресурс не найден | Запрошенная сущность не существует | GET деталей удалённой привычки | Показать ошибку |
| **409 Conflict** | Конфликт состояния | Операция невозможна из-за текущего состояния | Повторный инкремент в тот же день, дублирующее создание | Показать ошибку |
| **500 Internal Server Error** | Ошибка сервера | Непредвиденная ошибка на стороне бэкенда | Любой необработанный сбой | Показать экран ошибки |

**Дополнительно — клиентские состояния (без HTTP-кода):**

| Ситуация | Поведение клиента |
|----------|-------------------|
| Нет сети / хост недостижим | Экран «Нет соединения» |
| Таймаут соединения или сокета | Экран «Нет соединения» |

---

### Формат тела ошибки

При любом ответе с кодом `4xx` или `5xx` бэкенд **должен** вернуть тело в следующем формате:

```json
{
  "code": "MACHINE_READABLE_CODE",
  "message": "Human readable description"
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `code` | `String` | Машиночитаемый код ошибки (например, `"INVALID_OTP"`, `"NOT_FOUND"`) |
| `message` | `String` | Человекочитаемое описание (для логирования на бэкенде, клиент не показывает его пользователю) |

> Клиент **не отображает** `message` пользователю и **не логирует** его (PII-риск). Клиент показывает собственные локализованные строки, определённые по HTTP-коду.

Если тело ошибки отсутствует или не десериализуется — клиент обрабатывает ошибку по HTTP-коду с `error = null`.

---

### Формат списков

Все эндпоинты, возвращающие коллекции, оборачивают массив в объект:

```json
{
  "items": [ ... ]
}
```

Это касается как корневого ответа, так и вложенных коллекций, если у них нет своего смыслового ключа. Голый JSON-массив `[...]` в корне ответа **не используется**.

## 3.1 FeatureAuth — авторизация

### Описание модуля

Авторизация в Anchor построена на схеме **email → OTP**. Пароля нет. Пользователь вводит email, получает одноразовый код, вводит его — и получает пару токенов доступа.

Сессия OTP — временный объект на стороне сервера, идентифицируемый строкой `sessionId`. Клиент передаёт `sessionId` при верификации и повторной отправке кода.

**Все эндпоинты этого модуля не требуют Bearer-токена.**

**Сценарий авторизации:**

```
1. POST auth/otp/send    { email }            → { sessionId }
2. POST auth/otp/verify  { sessionId, otp }   → { accessToken, refreshToken, isFirstAuthorized }
   (если код не пришёл)
   POST auth/otp/resend  { sessionId }         → 204 No Content
```

После успешного `verify` клиент сохраняет токены и направляет пользователя:
- `isFirstAuthorized: true` → онбординг (выбор привычек)
- `isFirstAuthorized: false` → главный экран

---

### POST `auth/otp/send`

Инициирует сессию авторизации: создаёт OTP и отправляет его на указанный email.

**Метод:** `POST`  
**Путь:** `auth/otp/send`  
**Требует токена:** нет

#### Тело запроса

| Поле | Тип | Описание |
|------|-----|----------|
| `email` | `String` | Адрес электронной почты. Формат валидируется на клиенте до запроса |

#### Ответ: `200 OK`

| Поле | Тип | Описание |
|------|-----|----------|
| `sessionId` | `String` | Уникальный идентификатор OTP-сессии. Клиент хранит его и передаёт в `verify` и `resend` |

#### Примеры

```json
// Запрос
{
  "email": "user@example.com"
}

// Ответ 200 OK
{
  "sessionId": "3f8a21bc-4e10-4d2f-a981-d1e2f3a4b5c6"
}

// Ответ 400 Bad Request
{
  "code": "INVALID_EMAIL",
  "message": "Invalid email format"
}
```

---

### POST `auth/otp/verify`

Верифицирует OTP-код и при успехе выдаёт пару токенов доступа.

**Метод:** `POST`  
**Путь:** `auth/otp/verify`  
**Требует токена:** нет

> Клиент отправляет этот запрос автоматически при вводе 5-го символа кода — без нажатия кнопки.

#### Тело запроса

| Поле | Тип | Описание |
|------|-----|----------|
| `sessionId` | `String` | Значение из ответа `auth/otp/send` |
| `otp` | `String` | 5-значный цифровой код, введённый пользователем |

#### Ответ: `200 OK`

| Поле | Тип | Описание |
|------|-----|----------|
| `accessToken` | `String` | JWT. Используется в заголовке `Authorization: Bearer` |
| `refreshToken` | `String` | JWT. Используется для обновления `accessToken` через `auth/refresh` |
| `isFirstAuthorized` | `Boolean` | `true` — новый пользователь (онбординг); `false` — возвращающийся (главный экран) |

#### HTTP-коды ошибок (специфичные для этого эндпоинта)

| Код | Причина | Поведение клиента |
|-----|---------|-------------------|
| `400` | OTP-код неверный | Показывает ошибку под полем ввода; разрешает повторный ввод |

#### Примеры

```json
// Запрос
{
  "sessionId": "3f8a21bc-4e10-4d2f-a981-d1e2f3a4b5c6",
  "otp": "48291"
}

// Ответ 200 OK (новый пользователь)
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4...",
  "isFirstAuthorized": true
}

// Ответ 200 OK (возвращающийся пользователь)
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4...",
  "isFirstAuthorized": false
}

// Ответ 400 Bad Request (неверный код)
{
  "code": "INVALID_OTP",
  "message": "OTP code is incorrect"
}
```

---

### POST `auth/otp/resend`

Повторно отправляет OTP-код на email, привязанный к существующей сессии. Вызывается при нажатии «Отправить снова» — кнопка становится активной после таймера (60 секунд).

**Метод:** `POST`  
**Путь:** `auth/otp/resend`  
**Требует токена:** нет

> Сессия (`sessionId`) остаётся той же — новый код привязывается к существующей сессии.

#### Тело запроса

| Поле | Тип | Описание |
|------|-----|----------|
| `sessionId` | `String` | Значение из ответа `auth/otp/send` |

#### Ответ: `204 No Content`

Тело ответа отсутствует.

#### Примеры

```json
// Запрос
{
  "sessionId": "3f8a21bc-4e10-4d2f-a981-d1e2f3a4b5c6"
}

// Ответ 204 No Content (пустое тело)
```

---

### POST `auth/refresh`

Обновляет пару токенов. Клиент вызывает автоматически при `401` на любом запросе. Ручного вызова из продуктового кода нет — это полностью внутренняя механика сетевого слоя.

**Метод:** `POST`  
**Путь:** `auth/refresh`  
**Требует токена:** нет (вместо Bearer в теле передаётся `refreshToken`)

#### Тело запроса

| Поле | Тип | Описание |
|------|-----|----------|
| `refreshToken` | `String` | Действующий refresh-токен, выданный через `verify` или предыдущий `refresh` |

#### Ответ: `200 OK`

| Поле | Тип | Описание |
|------|-----|----------|
| `accessToken` | `String` | Новый JWT |
| `refreshToken` | `String` | Новый refresh-токен (клиент заменяет сохранённый) |

#### Поведение при ошибках

| Код | Причина | Поведение клиента |
|-----|---------|-------------------|
| `400` / `401` / `403` | Refresh-токен невалиден или отозван | Удаляет оба токена, направляет на экран авторизации |
| `5xx` / нет сети | Сервер недоступен | Токены сохраняются; пользователь видит экран ошибки |

#### Примеры

```json
// Запрос
{
  "refreshToken": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4..."
}

// Ответ 200 OK
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "bmV3UmVmcmVzaFRva2Vu..."
}

// Ответ 401 Unauthorized
{
  "code": "INVALID_REFRESH_TOKEN",
  "message": "Refresh token is invalid or expired"
}
```

## 3.2 FeatureAddiction — привычки

### Описание модуля

Управление привычками пользователя: онбординг-выбор при первом входе, список на главном экране, создание, редактирование, просмотр деталей, удаление.

Эндпоинты делятся на две группы:
- **`addictions/*`** — вызываются при онбординге (после первой авторизации).
- **`client/addictions/*`** — CRUD-операции над привычками конкретного пользователя.

Все эндпоинты требуют Bearer-токена.

---

### Сводная таблица эндпоинтов

| # | Метод | Путь | Ответ | Описание |
|---|-------|------|-------|----------|
| 3.2.1 | GET | `addictions/default-selection-groups` | 200 + тело | Каталог привычек для онбординга |
| 3.2.2 | POST | `addictions/save-selected` | 204 | Сохранить выбранные привычки |
| 3.2.3 | GET | `client/addictions/all` | 200 + тело | Все привычки пользователя |
| 3.2.4 | POST | `client/addictions/create` | 204 | Создать привычку |
| 3.2.5 | GET | `client/addictions/details/{id}` | 200 + тело | Детали привычки |
| 3.2.6 | POST | `client/addictions/increment/{id}` | 204 | Отметить выполнение за сегодня |
| 3.2.7 | PATCH | `client/addictions/update/{id}` | 204 | Обновить привычку |
| 3.2.8 | DELETE | `client/addictions/delete/{id}` | 204 | Удалить привычку |

---

### 3.2.1 GET `addictions/default-selection-groups`

Возвращает каталог привычек, сгруппированных по категориям. Вызывается один раз — при первом входе пользователя, до выбора привычек.

**Метод:** `GET`  
**Путь:** `addictions/default-selection-groups`  
**Тело запроса:** отсутствует

#### Ответ: `200 OK`

```
{
  "items": [ AddictionSelectionGroups ]
}
```

**`AddictionSelectionGroups`** (элемент `items`)

| Поле | Тип | Описание |
|------|-----|----------|
| `category_key` | `String` | Ключ категории. Допустимые значения — см. [«Категории привычек»](#категории-привычек) |
| `addictions` | `Array<AddictionSelectionItem>` | Привычки в категории |

**`AddictionSelectionItem`** (элемент `addictions`)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `Int` | Уникальный ID привычки в каталоге |
| `name` | `String` | Локализованное название |

> Элементы выбора не содержат `icon_key` и `gradient_key` — они не нужны на экране онбординга.

#### Пример ответа

```json
{
  "items": [
    {
      "category_key": "sport",
      "addictions": [
        { "id": 1, "name": "Бег" },
        { "id": 2, "name": "Плавание" }
      ]
    },
    {
      "category_key": "health",
      "addictions": [
        { "id": 4, "name": "Медитация" },
        { "id": 5, "name": "Сон 8 часов" }
      ]
    }
  ]
}
```

---

### 3.2.2 POST `addictions/save-selected`

Сохраняет список привычек, которые пользователь выбрал при онбординге. Вызывается один раз при завершении онбординга.

**Метод:** `POST`  
**Путь:** `addictions/save-selected`

#### Тело запроса

| Поле | Тип | Описание |
|------|-----|----------|
| `ids` | `Array<Int>` | ID привычек из каталога, выбранных пользователем. Лимит без подписки — 3 |

#### Ответ: `204 No Content`

Тело ответа отсутствует.

#### Примеры

```json
// Запрос
{
  "ids": [1, 4, 7]
}

// Ответ 204 No Content (пустое тело)

// Ответ 409 Conflict (превышен лимит)
{
  "code": "SELECTION_LIMIT_EXCEEDED",
  "message": "Selected addictions limit exceeded"
}
```

---

### 3.2.3 GET `client/addictions/all`

Возвращает все привычки текущего пользователя, сгруппированные по категориям. Вызывается при открытии главного экрана и после каждой мутации.

**Метод:** `GET`  
**Путь:** `client/addictions/all`  
**Тело запроса:** отсутствует

#### Ответ: `200 OK`

| Поле | Тип | Описание |
|------|-----|----------|
| `is_create_new_available` | `Boolean` | `true` — можно создать новую привычку; `false` — лимит достигнут |
| `items` | `Array<AddictionsAllGroup>` или `null` | Группы привычек. `null` или пустой массив — если привычек нет |

**`AddictionsAllGroup`** (элемент `items`)

| Поле | Тип | Описание |
|------|-----|----------|

## 3.3 FeatureAssistant — мотивационные цитаты

### Описание модуля

Виджет мотивационных цитат на главном экране. Клиент запрашивает одну актуальную цитату при открытии главного экрана. Цитата отображается в двух форматах:

- **Краткий** — одна строка в карточке-карусели.
- **Расширенный** — полный текст в выдвигающемся sheet, который открывается при нажатии на карточку.

---

### 3.3.1 GET `assistant/motivational-quote`

**Метод:** `GET`  
**Путь:** `assistant/motivational-quote`  
**Тело запроса:** отсутствует

#### Ответ: `200 OK`

| Поле | Тип | Описание |
|------|-----|----------|
| `text` | `String` | Краткий текст цитаты. Отображается в карточке. Рекомендуемая длина — до 80 символов |
| `detail_text` | `String` | Расширенный текст. Отображается в sheet при нажатии. Может быть длиннее `text` |

> Оба поля не могут быть `null`. Если краткая и расширенная версии одинаковы — допустимо передать один текст в оба поля.

#### Пример

```json
// Ответ 200 OK
{
  "text": "Маленький шаг каждый день — большая жизнь в итоге.",
  "detail_text": "Маленький шаг каждый день — большая жизнь в итоге. Не жди идеального момента, начни с того, что есть прямо сейчас."
}
```
